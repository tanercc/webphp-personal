# CMS reference repository and Personal example

- This repository is a standalone PHP 8.4 portfolio demo on SQLite (default) or MySQL. Do not modify other projects or copy their content, configuration, uploads, or users.
- For reuse, read `docs/mimari.md` and `docs/yeni-site.md` first. Personal remains the working example here. Use `tools/create-site.php` for a new project; do not copy the runtime database, sessions, uploads, secrets, or demo seed. New projects receive the guide in `starter/AGENTS.md`.
- Run `git status --short` first. This directory is the workspace root. The live database is `storage/personal.sqlite`; sessions and logs are excluded from Git.
- Composer/npm is not required. Preserve the existing panel and official packages. Do not patch vendor sources manually or replace the editor/file manager.
- `config/site.php` defines the installation name, profile, `database` (driver and SQLite file or MySQL host/port/name/user/charset), and session settings. Env overrides: `PANEL_DB_DRIVER`, `PANEL_DB_FILE` (`PERSONAL_DB_FILE` fallback), `PANEL_DB_HOST/PORT/NAME/USER/PASSWORD`. The MySQL password comes only from env or the Git-ignored `config/config.runtime.php` (`$databasePassword`). Preserve the reference demo's cookie name and SQLite default. `database/seed-base.php` contains neutral metadata and a home page, with no users. The starter installer creates an administrator with a password supplied through the environment and stores only its hash.
- `database/schema.php` is the single schema definition; `database/seed.php` contains fictional demo data only. Changing the data model: edit `schema.php` and the relevant seed, then reinstall a fresh database. There are no migrations; a site holding real data needs a separate plan before any schema change. Installation must not delete or overwrite an existing database. Never import a seed into a live database.
- MySQL requires >= 8.0.19, utf8mb4, InnoDB, and `utf8mb4_bin` on slug/code/email/limit_key; MariaDB is unsupported. `tools/install.php` builds from scratch: SQLite via temp file + exclusive publish; MySQL needs an empty database, takes an install lock, and a failed run drops only its own tables. `tools/verify.php` also checks that the database structure equals `schema.php`.
- Portable SQL in application code: backtick identifiers, single-quoted strings, `LIMIT n OFFSET m`, `COALESCE`, `LIKE ? ESCAPE '!'`. Do not use `IFNULL`, `||`, `GROUP_CONCAT`, `ON CONFLICT`, `ON DUPLICATE KEY`, `PRAGMA`, `information_schema`, `sqlite_master`, `SHOW`, `SQL_CALC_FOUND_ROWS`, `FOUND_ROWS`, `INSERT ... SET`, or SQL date functions. Engine differences live only in `panel/include/db_dialect.php`. `affected_rows` counts changed rows on MySQL but matched rows on SQLite, and `insert_id` is meaningful only right after an INSERT; rely on neither otherwise.
- Connection is `panel/include/database.php`, engine differences `panel/include/db_dialect.php`, schema and validation `panel/include/db_schema.php`, table creation `panel/include/db_install.php`. Keep values parameterized and preserve identifier, table, and field allowlists. The adapter covers only the query contract currently used by the panel.
- Panel/API/contact writes are validated against `schema.php` (`panelValidateWrite`, 422 `Invalid value: <column>`) on both engines.
- Preserve the HTTP API's `data/itemsCount`, string IDs, soft deletion, translations, and role/action/field/CSRF contracts. Forms use column types and defaults from `schema.php`.
- The site is built manually with PHP in `templates/pages` and `templates/partials`; do not introduce a theme engine. Installation-specific field labels belong in `config/panel-fields.php`. Render rich HTML only with `panelRichHtml()`; use `panelHtml()` / `e()` for other HTML contexts.
- The official theme files `css/styles.css`, `js/scripts.js`, profile image, and Bootstrap/font assets are unchanged. Sources and hashes are recorded in `docs/theme-*.json`. Custom CSS belongs in `css/site.css`. `assetAttributes`/`scriptAttributes` derive SRI and content versions from the same file bytes; do not remove this behavior.
- CKEditor is the only rich-text editor; do not bundle TinyMCE, Summernote, or other editors. The panel uses the CKEditor 4.22.1 standard package, not supported LTS. Keep `fullPage:false`, `disallowedContent:'script;style'`, and `versionCheck:false`. Do not distribute/enable samples or GeSHi. Enabling these features requires a new security assessment.
- Record media is database-authoritative: `media` + `media_lang` (title/alt/caption per language), uploaded only through `POST /panel/api/media` (`panel/api/media.php`) with the same session/role/CSRF rules and edit rights on the owner record. Allowed: jpg/jpeg/png/webp/gif/pdf, max 10 MB, extension must match the `finfo` MIME, images also pass `getimagesize`; SVG and everything else rejected. Files get server-generated names under `uploads/media/<owner_table>/<owner_id>/`; delete is soft. `image_id` on pages/sliders/menus/datas/cats/tags/users must reference an active media row of the same record (422 `Invalid value: image_id`).
- The file manager remains only for CKEditor images and `icon` paths. Preserve its shared authentication/CSRF checks and record scope through `RF.subfolder`. A missing folder must not fall back to the shared root. Remote URL loading, archive extraction, quick upload, and active-document writes remain disabled. Preserve SRI values for the local jQuery/UI files.
- The demo accepts only a genuine loopback `REMOTE_ADDR`. Local login uses hashed passwords, CSRF, rate limiting, and session ID rotation without CAPTCHA. Do not silently remove the loopback restriction to publish the site; assess production deployment separately. Never add an authentication-bypass endpoint for tests or users.
- The contact form saves messages locally and sends no email; no mail library is bundled. `datas` type 6 is the inbox; messages are rendered as plain text. Name <= 50, message 10-255 characters (`datas.info varchar(255)`). The IP limit is 5 messages per 15 minutes.
- `router.php` and Apache `.htaccess` protect app/config/database/docs/storage/tools/templates/tests/upstream, starter source files, and vendor examples from HTTP access. Under `/panel/`, only `index.php`, `api/index.php`, and the five file manager entry points execute PHP. Keep both rule sets equivalent when changing either. The PHP development server requires the router. Nginx needs equivalent rules.
- For PHP changes, lint the affected files and run `python tests/http-workflows.py`, `php tools/verify.php`, and `php tests/db-contract.php --driver=sqlite|mysql|both`. For DB-touching changes also run `python tests/http-workflows.py --driver mysql` with `PANEL_TEST_MYSQL_HOST/PORT/USER/PASSWORD` (creates and drops `cms_test_<hex>` databases); if MySQL is unavailable, say so in the report. Write tests must use disposable databases. Do not add unnecessary one-off test files.
- The public demo is Turkish by default. English translation records remain available in the panel; there is no separate public-language route. Generic CMS template choices do not automatically add Personal layouts; see the README content mapping.
